# 調査・再発防止

## 証拠
- ユーザー報告：英日対応の変更後、設定・管理画面や×の操作で空白・黒い画面が時々出る。
- 修正前：回帰テスト3件で26箇所のアサーションが失敗。画面内の閉じる→再表示を10回繰り返すと、設定・統計ウィンドウは各1個ではなく各11個残った。
- 修正とタブ整理後：XCTest 4件、失敗0。設定・統計の画面内／ネイティブの閉じる操作を各10回、本体の非表示・再表示、英日タイトルの表示中・非表示中の更新を検証。
- 修正前の断続的な空白・黒い画面そのものは撮影できていない。ウィンドウが蓄積する不具合は独立して再現済み。あらゆる描画不具合が解消したと断定しない。

## 5 Whys
1. なぜ古いUIが残り得る？ 補助ウィンドウが画面内の閉じる操作後も存続する。
2. なぜ存続する？ orderOutは隠すだけでネイティブのウィンドウを閉じない。
3. なぜ制御できなくなる？ 管理クラスが直後に参照をnilにする。
4. なぜ新しい画面が増える？ showはnilを未生成と判断する一方、AppKitには前の画面が残る。
5. なぜ見逃した？ ウィンドウ数の上限を確認する反復開閉テストがなく、画面内とネイティブの閉じ方が異なっていた。

## Fishbone
- 寿命管理：非表示とcloseの相違。AppKitに残るウィンドウの所有参照を捨てる。
- UI：長いスクロール内の閉じる。カレンダーとシステム設定の混在。
- 翻訳：表示更新は増えるが、英日対応前からcloseには同じ所有参照の問題があった。時系列だけで翻訳変更が導入原因とは断定しない。
- 初期化：NSApplicationの弱参照デリゲート。アプリバンドル外の通知処理は例外になるため、権限要求・配信の両方を保護。
- 検証：以前のPackageにはテストターゲットも反復開閉の回帰テストもなかった。

## 修正・再発防止
補助画面の閉じる操作をネイティブcloseに統一し、それぞれ1つの画面を保持して再利用。既存の翻訳とデータのバインディングは維持。設定は4タブと固定の閉じるボタン。今後はswift testとインストール済みアプリでの英日開閉確認を必須とする。コードレビュー済みで、指摘された通知配信側の保護を追加。

## 実画面で追加発見：カテゴリ編集
最初のカスタムカテゴリの鉛筆ボタンで、既存名を表示する編集画面ではなく空の「新しいカテゴリを追加」が開いた。設定画面・タイマー画面は表示Boolと対象カテゴリを別々に持ち、Boolによるシートが古いnilを捕捉していた。CategoryEditorRequestとsheet(item:)で表示と対象データを一体化。毎回新しいUUIDで入力状態も分離する。追加修正のレビューは残存指摘なし、最終テストは再度4/4成功。

5 Whys：編集モードが違う→対象カテゴリがnil→初回シートの古いデータ→表示Boolが対象データから独立→初回の入力済み編集確認がなかった。再発防止：初回編集、キャンセル後の再編集、編集後の新規追加を、テストデータを保存せず確認する。

## インストール済みアプリの確認
- 4タブを英語・日本語で確認。アプリタブのスクロール後もヘッダー・閉じるボタンが表示される。
- 日本語の統計画面：タイトルバー×→設定、再表示→内容のある統計、画面内の閉じる→設定を確認。
- 設定のタイトルバー×→内容のあるタイマーを確認。
- カテゴリ編集の初回は最初のカスタムカテゴリの名前・絵文字が入力済み。キャンセル後に別のカスタムカテゴリを開くと正しい対象になる。タイマーメニューの追加は空の新規画面を開く。
- ユーザー追加要望により、管理画面のカテゴリ一覧上にも翻訳対応の追加ボタンを設けた。
- 最終の修正差分レビュー：残存指摘なし。最終XCTest：4件、失敗0。
- 稼働ログのチェックサムはインストール前のバックアップと一致。テストカテゴリやカレンダー予定は保存していない。

最終インストール確認：/Applications/VisualBarTimer.appの実行ファイルのSHA-256はリリースビルドと一致。管理画面のカテゴリ→新しいカテゴリを追加で、翻訳対応の空の追加シートが開くことを確認。ユーザーが入力できるよう開いたままにしている。
